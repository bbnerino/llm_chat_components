## 1. 경험: 이전 프로젝트에서 무엇이 문제였나

자세한 분석은 `legacy-chat-perf-analysis.md`.

| 증상 | 원인 | 교훈 |
|---|---|---|
| 대화가 길어질수록 버벅임 | store 전체 구독, 렌더마다 새 객체를 만드는 getter가 `memo`를 무력화, 매 렌더마다 `scrollHeight`를 읽어 강제 reflow | 이벤트 1개의 비용이 **대화 전체 길이**에 비례하면 언젠가 반드시 느려진다 |
| 병렬 tool 호출 중 스피너가 하나만 돎 | tool 상태를 "그룹의 마지막 메시지인가(`isNew`)"로 **추정** | 상태는 추정하지 말고 서버가 callId 단위로 **선언**하게 한다 |
| tool이 실패해도 성공 체크 표시 | tool별 에러 상태가 없음 | View는 모든 상태(실행 중/성공/실패/취소)를 다뤄야 한다 |
| 대화를 전환하면 이전 대화 응답이 섞임 | 전역 store 하나 + 스트림을 끊지 않음 | 상태는 스레드별로 격리, reader의 수명은 화면이 아니라 run에 묶는다 |
| 중지해도 서버는 계속 생성(과금) | 프록시가 upstream fetch에 abort signal을 넘기지 않음 | 중지는 끝까지 전파돼야 한다 |
| "다시 시도" 버튼이 동작 안 함 | 콜백을 넘기지 않음 | — |
| 토큰 스트리밍 없음 | 이벤트 하나 = 말풍선 하나 | 텍스트와 tool이 섞인 **parts** 모델이 필요 |

**글에 쓸 문장 후보**: "코드만 보면 `memo`를 썼으니 최적화된 것처럼 보였다. 프로파일러를 켜고 나서야 매 렌더마다 모든 그룹이 새 객체로 복사되고 있다는 걸 알았다."

## 2. 고민: 문제를 어떻게 다시 정의했나

1. **LLM 응답은 데이터가 아니라 이벤트 스트림이다.** "받아서 보여준다"가 아니라 "끝을 알 수 없는 이벤트를 믿을 수 있는 상태로 바꾼다."
2. **연결과 run은 다른 것이다.** 연결은 언제든 끊긴다(모바일 백그라운드, 와이파이→LTE, 프록시 타임아웃, 새로고침). run은 끊기면 안 된다. 그래서 run을 서버 메모리에서 독립적으로 돌리고, 연결은 그 로그를 구독하는 창으로 만들었다.
3. **끊김 ≠ 중지.** 연결이 끊겼을 때 서버가 생성을 멈추면 이어받을 수 없고, 계속하면 탭을 닫은 사용자에게 과금된다. 그래서 중지는 명시적 cancel, 끊김은 아무것도 안 함, 오래 안 돌아오면 reaper가 정리.
4. **재시도의 기준은 "사용자가 이미 봤는가".** 보기 전이면 조용히 다시 시작, 본 뒤면 다시 생성하지 않고 이어받는다.
5. **reader는 React 바깥에.** 컴포넌트 effect에 두면 화면을 떠나는 순간 죽거나 엉뚱한 화면에 쓴다.

## 4. 직접 겪은 버그들 (글의 하이라이트 후보)

조사로 알게 된 것과 별개로, 이번 구현 중에 **직접 마주친** 것들. 재현 방법과 해결이 명확해서 글감으로 가장 좋다.

### 4-1. 프록시가 끊김을 삼켰다 (v1)
- 서버가 소켓을 끊었는데 Vite 프록시가 브라우저 쪽 연결을 유지 → UI가 영원히 "streaming".
- heartbeat는 **보내는 쪽 + 세는 쪽**이 있어야 완성된다 → idle watchdog.
- v2에서는 watchdog이 에러를 띄우는 대신 **이어받기**를 트리거한다. 로그: `fault: destroying socket at seq 15` → `resume after seq 14`.

### 4-2. 중지 한 번에 대화가 벽돌이 된다 — API로 직접 확인
- 짝 없는 `function_call`을 보내면 OpenAI가 `400 No tool output found for function call call_a.`
- 해결: 인자도 못 받은 tool은 지우고, 인자는 받았지만 결과 없는 tool은 `{"error":"cancelled_by_user"}`를 합성. 지우는 것보다 합성이 나은 이유: 모델이 "사용자가 멈췄다"는 맥락을 알아 다음 답변이 자연스럽다.
- 검증: 도쿄·뉴욕·파리 날씨 tool 3개 실행 중 Esc → 다음 메시지 정상 응답.

### 4-3. 한국어에서만 생기는 취소선
- "부산은 17.1~23.1도, 서울은 11.2~21.3도" → 중간이 취소선.
- GFM은 물결표 **한 쌍**도 취소선으로 해석한다. 한국어는 범위를 `~` 하나로 쓴다.
- `remarkGfm({ singleTilde: false })`. 영어로만 테스트하면 절대 못 잡는다.

### 4-4. Node가 해외 API에 연결을 못 했다 (curl은 되는데)
- 날씨 tool이 `fetch failed`. curl은 1.3초에 성공.
- 원인: Node의 Happy Eyeballs(`autoSelectFamily`)가 주소당 **250ms**만 기다린다. RTT 400ms 서버는 IPv4도 시간 안에 연결 안 되고, IPv6가 막힌 환경이면 둘 다 실패 → 285ms 만에 ETIMEDOUT.
- `net.setDefaultAutoSelectFamilyAttemptTimeout(2000)`. 덤으로 tool마다 타임아웃(8s)을 걸어 외부 API 하나가 run 전체를 붙잡지 못하게 했다.

### 4-5. 테스트가 잡은 순서 버그: 병합 → 중복제거 vs 중복제거 → 병합
- 프레임 단위 delta 병합을 넣었더니, `[seq2(중복), seq3(신규)]`가 하나(seq 2..3)로 합쳐진 뒤 "seq 2는 이미 봤음"으로 **통째로** 버려져 새 토큰까지 잃었다.
- 해결: 연속 구간만 먼저 남기고(contiguous) 그 다음 병합. 최적화는 정확성 경계 **안쪽**에서만 해야 한다.

### 4-6. 중지했는데 방금 받은 글자가 사라진다 (셀프 리뷰)
- `stop()`이 큐를 비우는 `killRun()`을 `flush()`보다 먼저 호출 → 받았지만 아직 그리지 않은 토큰이 버려짐.
- 순서 하나. "사용자가 본 마지막 글자 = 저장된 마지막 글자"가 깨지는 버그.

### 4-7. 취소된 tool이 계속 "조회 중" 스피너
- 리듀서는 run 종료 시 미완료 tool을 `cancelled`로 확정하는데, 날씨 카드 View는 `error`와 `output 있음`만 처리 → 나머지는 전부 로딩으로 그렸다.
- 이전 프로젝트에서 "실패해도 성공 체크"가 떴던 것과 같은 계열의 버그. **View는 모든 상태를 처리해야 한다.**

### 4-8. 바닥에 있는데 "맨 아래로" 버튼이 안 사라짐
- 높이가 바뀌는 순간 scroll 이벤트가 먼저 와서 "바닥 아님" 판정 → ResizeObserver가 위치를 보정해도 scrollTop이 그대로면 scroll 이벤트가 다시 안 옴 → 버튼 고착.
- ResizeObserver 콜백에서도 상태를 다시 계산.

### 4-9. 모델이 tool 대신 본문에 후속 질문을 씀
- 프롬프트에 "후속 질문은 tool로"라고만 쓰면 모델이 가끔 본문에 질문 목록을 쓴다.
- "본문에는 절대 쓰지 말 것, UI가 tool로 렌더링한다"로 계약을 명시. 프론트엔드가 프롬프트의 소비자이기도 하다는 사례.

## 5. 공통 컴포넌트와 처리 (설계 요약)

| 공통 요소 | 역할 | 재사용 포인트 |
|---|---|---|
| `SSEParser` / `readSSE` | 스펙 준수 증분 파서 + idle watchdog | 서버(업스트림)와 클라이언트(BFF)가 같은 코드 |
| `ChatTransport` | start / resume / cancel 3개 메서드 | 테스트는 async generator 하나로 시나리오 연주 |
| `ChatRuntime` | run 소유, 배칭, 재시도/이어받기, 수명 이벤트, 영속화 | React 비의존 → 다른 UI 프레임워크에서도 사용 가능 |
| `chatReducer` | 스레드 격리 + seq 가드 + tool 생명주기 | 순수 함수 → 49개 테스트 대부분이 네트워크 없이 |
| selector 훅 (`useMessage`, `useMessageIds`…) | 좁은 구독 | 행 컴포넌트는 자기 메시지만 |
| tool 레지스트리 (`defineTool`) | placement / label / View / isOutput 선언 | 새 tool 추가 시 렌더링 코드 변경 없음 |
| `parsePartialJson` | 스트리밍 인자의 "확정된 접두" 파싱 | 화면이 필요할 때만 파싱 (`streamArgs`) |
| `layoutParts` | parts → [텍스트 / 작업 묶음 / 고정 카드] + footer | 안정적인 key로 펼침 상태 유지 |
| `StreamingMarkdown` | 블록 memo + 꼬리 보정 + 안전한 URL | 문서 패널에서도 재사용 |

## 6. 검증

- **테스트 49개**: 파서(청크 경계 전수, UTF-8, CRLF, watchdog), partial JSON(모든 접두), 리듀서(격리·seq·tool·병합), 런타임 통합(끊김→이어받기, 완료 없는 종료, 429 재시도, 서버 실패 재시도, 중지, 대화 전환, single-flight, **새로고침 후 이어받기**), 이력 정리, Markdown 보정, 레이아웃.
- **브라우저 실측** (장애 재현 패널):
  - 응답 중 끊김 → `이어받기 1회`, 텍스트 중복·누락 없음
  - 429 → "3초 후 다시 시도합니다" 카운트다운 → 자동 성공
  - tool 실행 중 중지 → 다음 메시지 정상 (벽돌 방지)
  - 대화 전환 → 사이드바에 생성 중 표시, 다른 대화로 섞이지 않음
  - 새로고침 → `resume after seq 142 (log=150, running)`, 이어서 스트리밍
- **번들**: API 키 미포함 확인.

## 7. 아직 하지 않은 것 (정직하게)

- 렌더 횟수 벤치마크("이전 방식 vs 개선 방식")는 아직 측정하지 않았다. 글에 수치를 넣으려면 React Profiler로 측정 필요.
- 코드 하이라이팅, 메시지 트리(편집/분기), 멀티 탭 동기화, 다중 인스턴스(Redis)는 로드맵.
- Safari 실기기 IME 테스트는 하지 않았다(가드는 이슈 보고 기반으로 구현).
